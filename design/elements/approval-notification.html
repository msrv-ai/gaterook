Approval notification

How one approval request reaches the approver outside the window: the desktop notification, Slack, Telegram and the in-app toast, with the same fields as the request. Used in Approvals (delivery channels) and in Settings · Notifications.

Theme

Desktop notification

Shown by the OS while the window is in the background. Review and Deny only: nothing is approved blind from a notification.

Desktop notification

macOS Notification Center and the Windows notification area, sent for sql_execute on dev-db.

Review opens the request in the app

There is no Approve button in the notification: approving needs the exact action on screen. Deny works from here.

Slack message

Block Kit layout from kit parts: header, fields, the full statement, context and buttons. A direct message to each linked approver is the recommended default: the exact action can hold customer data, and everyone in a channel would see it. This workspace (acme) posts to the channel #deploy-approvals, chosen in Settings › Notifications. The agent's note is never sent.

SSlack

Posted by the GateRook app to #deploy-approvals in the acme workspace. The buttons act only for you, the linked approver.

Direct messages to linked approvers are recommended

Approve and Deny work only for approvers who linked their Slack account in Settings › Notifications. Posting to a channel such as #deploy-approvals is a choice there, with the hint “Everyone in the channel sees the exact action”; in a channel, anyone who isn't a linked approver gets a private reply with Open in app. A statement over 3,000 characters is not cut: Approve is dropped and Open in app remains, and so it is for every prod request and whenever the policy requires a comment.

Telegram message

A bot message with the statement in a code block and an inline keyboard under it. Telegram is not set up in this workspace (Settings › Notifications); this is what each linked approver gets once a bot is added.

TTelegram

Sent by the GateRook bot to each linked approver.

Only linked approvers get this message

Each approver starts the bot and confirms the code from Settings · Notifications. Over 4,096 characters the statement is not cut: Approve is dropped and Open in app remains, as it is for every prod request and whenever the policy requires a comment.

A production request, in every channel

Prod never hides in a caption or a small chip: every channel titles it “PROD · Approval needed” and the first line says it runs on production. Slack and Telegram never offer Approve for prod, whatever the comment rule: they keep Deny and Open in app, and the decision is made in the app; the desktop notification is always Review and Deny. Same request: runbook restart-api on prod-vm through incident-prod, 10 min before auto-deny.

Desktop, prod

macOS; Windows uses the same text.

SSlack, prod

In #deploy-approvals. A prod request is approved only in the app, so the message keeps Deny and Open in app.

TTelegram, prod

Prod is approved only in the app, with or without a required comment.

In-app toast

While the window is in front, a toast with Review replaces the OS notification. It stays until it is used or dismissed.

In-app toast

Bottom-right of the window; the titlebar bell keeps the count.

The toast never holds the decision

Review opens the request in Approvals. Dismissing the toast leaves the request waiting there.

After a decision or a timeout

Channel messages are edited in place: the buttons give way to the outcome, so nobody acts on a request that is already closed.

SSlack, approved in the app

An earlier request's message, edited at 12:21:18 when you approved it.

TTelegram, expired

No decision in 10 min (the stage window); the keyboard is removed.
