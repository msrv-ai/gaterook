# Control AI access to Amazon Athena

GateRook's MCP Firewall lets AI apps explore Athena's data catalogs and run SQL reads that Athena's own plan confirms, within a workgroup's limits, and holds every change for your review. With an IAM role, AWS itself limits each call to what it needs. The [security model](security.md) explains execution controls, explicit Bypass, and the append-only, tamper-evident audit trail.

## Connect a workgroup

The built-in **Amazon Athena** connector (`athena`) calls Athena's JSON API in one region, signed with SigV4. There is no Athena SDK in GateRook; requests go only to `athena.<region>.amazonaws.com` (`.amazonaws.com.cn` in China). Choose:

- the **region** and the **workgroup** every query runs in (`primary` by default);
- the **data catalog** of names without one (`AwsDataCatalog`, the AWS Glue catalog, by default) and optionally a **default database**;
- the **databases** agents may use: `database` in that catalog, or `catalog.database`, with `*` matching any characters. Empty, every database the credentials may read;
- optionally a **query results location** (`s3://bucket/prefix/`), used unless the workgroup sets its own; leave it empty for a workgroup that keeps results itself;
- the **credentials**, as for [Amazon DynamoDB](dynamodb.md): an access key (stored encrypted in GateRook) or an AWS profile of this computer, optionally a **role to assume** with an external ID in its trust policy.

The workgroup is the cost boundary: Athena charges for the data a query scans, and only the workgroup's per-query data usage control (`BytesScannedCutoffPerQuery`) stops a query that would scan too much. GateRook stops a query at the call's deadline, which bounds its time, not its bytes. **Test connection** reports the identity AWS sees (`sts:GetCallerIdentity`), reads the workgroup with `GetWorkGroup` (its state, engine version and data limit), lists the databases agents may use, and runs `EXPLAIN SELECT 1`, which scans nothing and costs nothing, to prove that queries start and their results can be read. It warns when the workgroup has no per-query data limit, and when it doesn't override client-side settings, so its results location and encryption don't hold for every query.

While you fill in the form, GateRook suggests the profiles of `~/.aws/config` and fills in the profile's region. Once the form can sign in, it lists the workgroups, data catalogs and databases and offers the workgroup's results location, under a session policy that allows only `athena:ListWorkGroups`, `GetWorkGroup`, `ListDataCatalogs`, `ListDatabases` and Glue's catalog and database names: no query runs. It says so when the workgroup doesn't exist or has no results location.

### Session policies

With a role, **Session policy** defaults to each call's own permissions, enforced by AWS whatever the role itself may do. On prod it can't be turned off.

- GateRook first reads the workgroup's settings with a policy that allows only `athena:GetWorkGroup` on that workgroup, to learn where its results go. It keeps them for ten minutes.
- A read gets `athena:StartQueryExecution`, `StopQueryExecution`, `GetQueryExecution`, `GetQueryResults` and `GetWorkGroup` on the connection's workgroup only; Athena's metadata reads (`athena:List*`, `GetDataCatalog`, `GetDatabase`, `GetTableMetadata`); Glue's catalog and database names (`glue:GetCatalog*`, `glue:GetDatabase*`); Glue's tables and partitions (`glue:GetTable*`, `glue:GetPartition*`, `glue:BatchGetPartition`) of the listed databases only; S3 reads (`s3:GetObject`, `s3:ListBucket`, `s3:GetBucketLocation`, `s3:ListBucketMultipartUploads`) and `lakeformation:GetDataAccess`; and S3 writes (`s3:PutObject`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`) under the results location only. A read can't change a table, a partition or any S3 object but its results. S3 reads aren't limited to buckets, as a table's data can be anywhere: the role's own permissions bound them.
- An approved change also gets Glue's changes of tables, partitions and the database itself (`glue:*Table`, `glue:*Partition`, `glue:*Database`) in its target's database only, and S3 writes and deletes, which follow the role's own permissions, as Athena writes a table's files where its location says.

STS takes at most 2,048 characters of session policy: a database list too long for that keeps the actions and allows the Glue tables of every database, still without any write. Federated catalogs (Lambda connectors) need `lambda:InvokeFunction`, which the generated policy doesn't grant. Without a role, each call has every permission of the key or profile: **Test connection** says so, as a warning outside dev.

## Bound reads and review exact changes

| Tool | What it does | Default mode |
| --- | --- | --- |
| `athena_list_catalogs` | Data catalogs agents may use | Read only |
| `athena_list_databases` | Databases agents may use in one catalog, with `nextCursor` | Read only |
| `athena_list_tables` | Tables and views of one database, with `nextCursor` | Read only |
| `athena_describe_table` | Columns with types and comments, partition keys, the table type, format and location | Read only |
| `athena_query` | One `SELECT`, `WITH`, `VALUES`, `SHOW`, `DESCRIBE` or `EXPLAIN` | Read only |
| `athena_execute` | One `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE`, `ALTER`, `DROP`, `MSCK REPAIR TABLE`, `OPTIMIZE` or `VACUUM` | Approval |

Athena engine version 3 runs queries and DML with Trino and most DDL with Hive, so GateRook reads each statement by both: Trino's `'…'` strings, `"…"` names and comments, and Hive's backquoted names. Where the two engines would read a text differently, the statement is refused rather than guessed at: a statement Athena runs with Hive may hold no backslash in a string or a name, and no block comment. GateRook also refuses what it can't read with certainty (an open quote or comment, a control character, a character outside ASCII in the code) and more than one statement; a final semicolon is left out of what is sent. It never runs `UNLOAD`, which writes query results to S3, external functions (`USING EXTERNAL FUNCTION`, which call Lambda or SageMaker), prepared statements, session statements, `GRANT` and `REVOKE`, transactions, or `EXPLAIN ANALYZE`, which runs and bills its query; nor table functions other than Trino's built-in `sequence` and `exclude_columns`, as a federated catalog's pass-through query runs any SQL in its source.

Before a query runs, Athena plans it: GateRook runs `EXPLAIN (TYPE IO, FORMAT JSON)` with it, which scans no data and isn't charged, and runs the query only when the plan names no table it writes and every table it reads is in a database of the connection. Tables read through a view count as the tables the plan reports. `SHOW` and `DESCRIBE` run in Athena's Hive engine, which no plan covers: GateRook checks the database or table they name instead, and `SHOW DATABASES` is refused while the connection lists databases. After a query runs, the statement type Athena reports is checked once more: a read it reports as a change returns nothing.

GateRook polls a running query until it ends and stops it (`StopQueryExecution`) at the call's deadline. Each answer reports the data scanned. Values keep Athena's column types: an integer is a JSON number only where JavaScript keeps it exact, decimals stay text, doubles are numbers while finite, timestamps are ISO 8601, binary values show their first 256 bytes in hex. Arrays, maps and rows arrive as Athena's own text (`[1, 2]`, `{a=1}`) and stay that text. A large result returns `nextCursor`, sealed by GateRook, with the query's execution id and Athena's `NextToken`: it reads the next rows of the same execution without running the query again, and a page cut at the response size goes on at the next row. Cursors belong to one connection and one statement.

`athena_execute` runs one change. While the connection lists databases, its target must be in one of them, named as `database.table` or in the default database. GateRook never asks Athena to plan a write before a person approves it: Trino plans a write through the catalog's write hooks, which begin the write in the catalog (Trino's `memory` catalog creates the table of a `CREATE TABLE AS` while its `EXPLAIN` is only being answered). For a change Athena runs with Trino (`INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE TABLE AS`), GateRook plans a read of what the change reads instead, cut from the statement's own tokens: the query of an `INSERT` or a `CREATE TABLE AS`, `SELECT 1 FROM t WHERE …` for a `DELETE`, the new values for an `UPDATE`, and every `AND` condition and every value of a `MERGE` over its target `FULL JOIN` its source. A change whose read can't be built with certainty, such as a `MERGE` whose source is itself a join, is refused. The approval shows the exact statement, the table it writes as the statement names it, with the connection's catalog and default database, and the tables Athena's plan of the read names; `OPTIMIZE`, `VACUUM`, views and a Hive statement have no plan, and Athena checks them when it runs them. The approval also shows the workgroup's data limit. A statement whose read Athena refuses, a read, or one that reads or writes outside the listed databases is never put to a person; what only the write itself would show is Athena's answer to the approved statement. What runs is the approved statement, started once with a request token derived from the approval, so Athena never starts it twice. A change is never retried: an answer lost after the request was sent, or a change still running at the deadline, which GateRook stops, reports the outcome as unknown. Iceberg tables take a change whole or not at all; a failed `INSERT` or `CREATE TABLE AS` on a Hive table can leave data files in its location, so check the table before retrying.

## Boundaries

GateRook decides what it sends: the statement kinds above, Athena's plan of each query, the listed databases, the deadline and the row and size limits. AWS decides what the credentials may do: the role, the session policy GateRook generates, Glue and Lake Formation permissions. The workgroup decides what a query may cost and where its results go.

## Verify

The connector's tests run against a fake of Athena's JSON API and STS in every build: the SigV4 headers, the session policies' contents, polling, the stop at the deadline, sealed cursors over a query's results and the errors Athena answers. There is no Athena emulator (moto's Athena runs no SQL), and nothing here was checked against AWS, including Athena's plans of the reads GateRook builds for changes. Athena documents `EXPLAIN (TYPE IO, FORMAT JSON)`; GateRook reads its answer as Trino writes it and refuses a query whose plan it can't read, so a different format fails closed. JVM checks do not establish native-image or installer compatibility.
