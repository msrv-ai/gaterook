# Control AI access to Azure Cosmos DB

GateRook's MCP Firewall lets AI apps read Azure Cosmos DB for NoSQL with bounded SQL queries and point reads, and holds every change for your review. With a read-only key, Azure itself refuses every change; with Microsoft Entra ID, the service principal's data-plane roles are the boundary. The [security model](security.md) explains execution controls, explicit Bypass, and the append-only, tamper-evident audit trail.

## Connect with a read-only key or Microsoft Entra ID

The built-in **Azure Cosmos DB** connector (`cosmosdb`) calls Cosmos DB's REST API (`x-ms-version: 2020-07-15`) of one account for the API for NoSQL. There is no Azure SDK in GateRook. Requests go only to the **Account endpoint**, which must be an Azure Cosmos DB host: `https://<account>.documents.azure.com` (a regional endpoint such as `<account>-westeurope.documents.azure.com` too), `.documents.azure.us` in Azure Government or `.documents.azure.cn` in Azure operated by 21Vianet, on port 443. The only other endpoint is the emulator on this computer (`localhost`, `127.0.0.1` or `[::1]` with its port). TLS is verified against the system's certificate authorities, plain HTTP is accepted only for the emulator and only in development builds, no proxy is used and redirects are never followed, so a key's signature or a token never travels elsewhere.

Choose how GateRook signs in:

- an **Account key** (stored encrypted in GateRook). Each request carries Cosmos DB's master-key token: an HMAC-SHA256 signature of the request's verb, resource type, resource link and date, made with the key; the key itself never leaves this computer. Use the account's **read-only key** and select **Read-only key**: Azure refuses every change made with it, and GateRook then doesn't offer `cosmosdb_execute`. GateRook can't tell a read-only key from a read-write one without writing, so say which one you paste. A primary or secondary (read-write) key can change or delete anything in the account, databases included: **Test connection** warns about it outside dev, and every approval says that the key isn't limited to the change.
- **Microsoft Entra ID** with a service principal: its directory (tenant) ID or one of the tenant's domains, its application (client) ID and a client secret (stored encrypted). GateRook asks the tenant's token endpoint (`login.microsoftonline.com`, `login.microsoftonline.us` in Azure Government, `login.chinacloudapi.cn` in Azure operated by 21Vianet) for a token for `https://<account host>/.default`, or for `https://cosmos.azure.com/.default` when a public-cloud tenant has no resource for the account (`AADSTS500011`), and keeps it until five minutes before it expires. Cosmos DB's data-plane roles are the boundary: assign **Cosmos DB Built-in Data Reader** (`00000000-0000-0000-0000-000000000001`) to read, or **Cosmos DB Built-in Data Contributor** (`…0002`) for approved changes, scoped to the databases or containers agents use (`az cosmosdb sql role assignment create --scope /dbs/<database>/colls/<container>`). Azure roles such as Reader or Contributor don't give access to data. Test connection names the principal's object ID for the assignment.

Keys, signatures, tokens and the client secret are never shown, logged or put into a message, and every one of them is masked in answers.

**Databases** lists the databases agents may use, and **Containers** the containers: a container ID such as `orders` (in every allowed database) or `database/container` such as `app/customers`; `*` matches any characters. Empty lists allow every database and container the credentials may read. Both lists are enforced when GateRook classifies a call, without I/O, and again on every request. **Read consistency** asks queries and point reads for Session, Consistent prefix or Eventual consistency instead of the account's default; Cosmos DB refuses a level stronger than the account's, and Test connection warns about one. Under **Advanced**, **Cross-partition queries** off makes every query name its partition key value, **Pages per query** bounds the pages one call reads, and **Largest change** lowers the 2 MB a change may send.

Test connection reads the account (its regions and default consistency), lists the databases agents may use and names the identity: the key kind you selected, or the service principal. A principal whose roles are scoped to databases may not list the account's databases: then `cosmosdb_list_databases` looks up the databases named in the connection's list (without `*`) one by one.

## Bound reads and review exact changes

| Tool | What it does | Default mode |
| --- | --- | --- |
| `cosmosdb_list_databases` | IDs of the databases agents may use | Read only |
| `cosmosdb_list_containers` | Containers of one database, with their partition key paths | Read only |
| `cosmosdb_describe_container` | Partition key, indexing policy, default time to live, unique keys and throughput | Read only |
| `cosmosdb_query` | One Cosmos DB SQL `SELECT` on one container, with `@name` parameters | Read only |
| `cosmosdb_read_item` | One item by its id and partition key value, with its `_etag` | Read only |
| `cosmosdb_execute` | One create, upsert, replace, patch or delete of one item | Approval |

GateRook checks every database, container and item ID before it becomes part of a resource link and percent-encodes it itself: a slash, a backslash, a control or invisible formatting character, `.` or `..`, and in database and container names `?`, `#` or a trailing space are refused. A partition key value is a string of at most 2,048 bytes without control characters, a number Cosmos DB stores exactly (an integer up to 2^53), `true`, `false` or `null`, or an array of up to three of them for a hierarchical key; the header carries it in ASCII.

A query is one `SELECT` (Cosmos DB's query language only reads). Its parameters are an object such as `{"@status": "paid"}`. With `partitionKey` it reads one partition; without it GateRook sets `x-ms-documentdb-query-enablecrosspartition` and the query fans out over every partition, paying request units for each. The limit becomes `x-ms-max-item-count`, capped at the endpoint's rows; a call reads up to **Pages per query** pages (five by default) to fill it, as a page across partitions may be empty, and returns `nextCursor` where Cosmos DB stopped. Cursors are sealed by GateRook and belong to one connection and one query. Every answer reports the request units it used. Long strings are cut to the endpoint's cell size. An answer that reaches the endpoint's response size stops at the last whole page, and its cursor reads the next page from its start. Within the first page it keeps what fits, a first item too large on its own with the properties that fit, and goes on with a cursor only when that page was read to its end; otherwise it asks for a smaller limit or fewer properties.

### What Cosmos DB's gateway runs without an SDK

Cosmos DB pages a query with continuation tokens that keep no state of the query itself, and its SDKs add a client-side query pipeline for what needs one. GateRook calls the REST gateway directly, so:

- Across partitions the gateway runs filters and projections (`JOIN` within an item included) and refuses `TOP`, `ORDER BY`, `OFFSET LIMIT`, `DISTINCT`, `GROUP BY` and aggregates with `400` (substatus 1004, "can not be directly served by the gateway"). GateRook returns that refusal as an error that names the clauses from the gateway's query plan and suggests `partitionKey`. It never answers with what one partition returned.
- In one partition Cosmos DB runs them, but a page of such a query is exact only while it is the whole answer. GateRook reads the query's words outside string literals (conservatively: a subquery or a comment counts too) and never continues such a query page by page. An aggregate or `GROUP BY` whose answer comes in more than one page is an error; `TOP`, `ORDER BY`, `OFFSET LIMIT` or `DISTINCT` returns its first page, which is the exact beginning of the answer, marked as partial and without a cursor. Ask for a larger limit or narrow the query.

### Changes

`cosmosdb_execute` sends exactly one request: `POST …/docs` to create (refused if the id exists in the partition) or upsert (`x-ms-documentdb-is-upsert`: create, or replace the whole item), `PUT …/docs/<id>` to replace the whole item, `PATCH` with up to ten operations of Cosmos DB's partial document update (`add`, `set`, `replace`, `remove`, `incr`, `move`) and an optional `condition` such as `FROM c WHERE c.status = 'open'`, or `DELETE`. Every change names the item's partition key value, and `ifMatch` with the item's `_etag` from `cosmosdb_read_item` makes it apply only to that version. A patch can't change the item's id, its system properties or its partition key.

Before the approval exists, GateRook reads the container once and refuses a change whose partition key doesn't match the item's own value at the container's partition key paths, or a patch of the partition key. The approval shows the exact HTTP request: method, URL, Cosmos DB's headers and the body as it is sent. What runs is the approved request, read back and checked again, not the call's arguments. A change is never retried: a connection lost after the request was sent, a timeout or a server error reports the outcome as unknown. A body larger than Cosmos DB's 2 MB, the connection's limit or the endpoint's request size is refused, and an integer beyond 2^53, which Cosmos DB doesn't store exactly, is called out in the approval.

Refusals say what happened and what to do: an id that exists (409), a changed ETag or a condition that doesn't hold (412), a throttled request (429, with Cosmos DB's retry time; GateRook doesn't retry it), a key that can't write ("This key can't write"), a missing data-plane role, the account's firewall, or disabled key authentication. Masking applies to answers; filters run in Cosmos DB and compare the values stored there.

## Verify with the emulator

The connector's tests run against a fake of Cosmos DB's gateway that recomputes every request's master-key signature and checks it, Microsoft's published signature example, and a fake of Microsoft Entra ID's token endpoint. The integration test runs against the [Azure Cosmos DB Linux emulator vNext](https://learn.microsoft.com/en-us/azure/cosmos-db/emulator-linux), which runs on x86-64 and ARM64 and takes about 700 MB. Start the opt-in [service](../test-services/README.md) with `scripts/test-services.sh up cosmosdb` and run `scripts/test-services.sh run mvn -B -ntp -pl connectors/cosmosdb -am verify -Pservices,cosmosdb-it`.

The emulator checks no key or token and differs from Azure: it runs `TOP`, `ORDER BY` and aggregates across partitions in one answer, ignores the page size of sorted queries and implements no request units, throughput or data-plane roles. Microsoft Entra ID, Azure Government, Azure operated by 21Vianet, throughput and the gateway's refusals are verified against the fakes only. JVM checks and emulator tests do not establish native-image or installer compatibility, nor behaviour against an Azure Cosmos DB account itself.

Microsoft documents the [Cosmos DB REST API](https://learn.microsoft.com/en-us/rest/api/cosmos-db/), [access control and the master-key token](https://learn.microsoft.com/en-us/rest/api/cosmos-db/access-control-on-cosmosdb-resources), [queries through the REST API](https://learn.microsoft.com/en-us/rest/api/cosmos-db/querying-cosmosdb-resources-using-the-rest-api), [partial document update](https://learn.microsoft.com/en-us/azure/cosmos-db/partial-document-update), [data-plane roles](https://learn.microsoft.com/en-us/azure/cosmos-db/reference-data-plane-security) and [service limits](https://learn.microsoft.com/en-us/azure/cosmos-db/concepts-limits).
