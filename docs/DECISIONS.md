# Product decisions

Accepted product decisions take precedence over exploratory research. Dates identify when a decision was made; they do not imply that every resulting change has shipped.

| # | Date | Decision | Consequences |
| --- | --- | --- | --- |
| 1 | 2026-10-23 | Build the desktop application first: Electron, Angular, and a loopback core. | One local user, with decisions attributed to “you.” Server-mode identity, OIDC, roles, a hosted gateway database, and Docker/Helm deployment are outside the desktop scope. Disposable Docker test services remain useful. |
| 2 | 2026-10-23 | Use a GraalVM native core for fast API startup. | The same source runs on JVM 25 for development and tests. Dynamic Java plugins run in a separate JVM host; core dependencies must support native image. See [native-image research](research/15-graalvm-native.md) and [plugin-host research](research/16-plugin-host.md). |
| 3 | 2026-10-23 | Use Spring Data JPA and Hibernate for the gateway database. | SQLite with the community dialect, Flyway migrations, and schema validation. Spring AOT must retain the same behavior. The SQL connector still uses JDBC directly for user databases. |
| 4 | 2026-10-24 | Resolve the documented implementation choices using the accepted architecture. | The resulting product choices are recorded below; this historical decision does not grant blanket authorization for unrelated future actions. |
| 5 | 2026-10-24 | Defer a separate OS account for the core. | The OS user account remains the trust boundary. A process with the same account's privileges retains substantial access. |
| 6 | 2026-10-24 | Defer hardware-backed user-presence confirmation for approval and consent. | Content protection, a 700 ms activation delay, and no Enter-to-approve reduce accidental activation but do not establish a trusted human-presence boundary. |
| 7 | 2026-10-24 | Defer upstream OAuth for external MCP servers. | Configure upstream authentication with a secret passed through the server environment or HTTP headers. Superseded by decision 13 for servers at a URL. |
| 8 | 2026-10-24 | Bundle cloudflared; download ngrok only when selected. | Verify pinned SHA-256 hashes before execution. |
| 9 | 2026-10-24 | Keep SSH inside the native core. | Adapt MINA SSHD for native use first; consider sshj only if needed, and a separate JVM process only as a last resort. |
| 10 | 2026-10-24 | Application behavior follows accepted decisions when interface copy differs. | Keep reusable styles and components consistent. Update interface copy deliberately and verify behavior and accessibility. |
| 11 | 2026-10-27 | The product name is GateRook and the slug is `gaterook`. | The default home is `~/.gaterook`, with no import, reading, or modification of `~/.mcp-gateway`. Deep links, bridge bundles, package names, and branding follow the new name. Java/Maven and MCP metadata use `ai.msrv.gaterook`; first-party plugin packages use `gaterook.plugins.*`. Keep `GW_*` and `gateway.*` configuration names. |
| 12 | 2026-10-27 | Keep the complete application and local build in this public repository. | Include source, runtime assets, build manifests, locks, local tools, architecture, and curated research. README must document build and launch commands. All documentation is English. Internal AI files and progress logs are excluded; root `ai/` is ignored and must never be committed. |
| 13 | 2026-11-01 | GateRook signs in to remote MCP servers with OAuth itself. | A server is added by its URL or a pasted client configuration and signed in to in the person's browser. GateRook is the OAuth client, under the client ID of the person's OAuth app when one is configured. Otherwise, where the authorization server accepts Client ID Metadata Documents and public clients, its client ID is GateRook's own document, `https://gaterook.com/oauth/gaterook-client.json`, as the MCP authorization specification prefers; elsewhere GateRook registers dynamically under its own name (deprecated in the 2026-07-28 revision). It listens on this computer for the redirect, and keeps the tokens as an encrypted secret of the server that it renews. AI apps and agents never receive them. GateRook does not present another application's client ID, name or redirect URI. The document's URL must stay stable and published. Servers that admit only approved clients need the vendor's approval or a key in a header. |
| 14 | 2026-11-03 | External MCP servers reach agents with what they offer beyond tools. | GateRook speaks `2026-07-28` and `2025-11-25` back to `2024-11-05` to them, over stdio, Streamable HTTP and the older SSE transport. A server shares its resources and prompts only when the person lets it; reading them is a READ of the connection without approval, under the endpoint's policy, audit and masking. The MCP Apps of its reviewed tools, and images, audio and embedded resources in results, reach agents; bytes that contain a secret handed to the call are withheld, never altered. A call's progress, log messages and cancellation pass through, clients that listen hear list changes and resource updates, and a call can run as a task that waits for its approval. This supersedes the initial result policy in [extensibility research](research/11-extensibility.md) §3. |
| 15 | 2026-11-05 | Position GateRook as a desktop MCP Firewall for AI access to production infrastructure. | Lead with encrypted credentials, scoped connector access, exact-action approvals, and append-only, tamper-evident audit logs. Claims follow the [security model](security.md): protection applies to calls routed through GateRook, Bypass remains explicit, retention remains configurable, and the OS account remains the trust boundary. This changes product language, not runtime or compatibility identifiers. |
| 16 | 2026-11-11 | An endpoint with a long tool list publishes a search instead of every tool. | `auto` is the default: above 40 tools or 100 KB of definitions, `tools/list` shows GateRook's own tools, the 10 agents call most on the endpoint and those of pinned connections, says which connections have more, `find_tools` finds them, and `call_tool` or `call_read_tool` runs them under their own modes, approvals and audit. Each endpoint can list every tool or always search. Existing endpoints above the threshold change on upgrade, and clients reload their list on `list_changed`. See [searched tool lists](ARCHITECTURE.md#57-searched-tool-lists). |
| 17 | 2026-11-11 | Verified profiles of vendors' own MCP servers only make their defaults stricter. | GateRook ships checked profiles of cloud vendors' official servers with the build. A profile matches a server by its address or command, however it was added. It starts tools that run code or arbitrary API calls, return credentials, hand requests to another agent or spend money in Approval (Off until 2026-11-12 for the last two), and keeps them out of Read only whatever the server declares. Its setup URL sets the vendor's read-only switches, and the review warns when one is missing. It never makes a tool Read only, never rewrites a URL the person changed, and verifies no server behavior. See [verified profiles](mcp-servers.md#verified-profiles-for-cloud-platforms). |
| 18 | 2026-11-12 | Deliver connectors with heavy driver stacks as modules; compile the rest into the core. | [`connectors/delivery.json`](../connectors/delivery.json) records each connector. A connector that the native image can't hold, or that adds more than 3 MB to it without a listed reason, is a module: it is not in the installer, runs in a JVM host, and is downloaded and verified from a signed index when a person chooses it, without a confirmation. A first-party module keeps its connector type ids, tool names and default modes, so a connection behaves the same either way. PostgreSQL, MySQL, SQLite, MongoDB, Redis, SSH, the log services, Kubernetes, HTTP and MCP servers stay compiled in. Cassandra is the first module; Neo4j, Oracle and SQL Server follow. Moving every connector out was rejected: the connectors are a fifth of the installed size, and each module needs a Java runtime that would outweigh the light ones. See [connector delivery](connector-delivery.md). |
| 19 | 2026-11-12 | A connector module is a built-in connector with another delivery, installed without a review. | Its types keep the kind, tool names and default modes of compiled-in connectors, and the core takes the connector's own classification and exact action. That trust comes from one place only: the module channel, a signed index under its own keys. Anything that needs a missing type installs its module, including a call after a restored backup. See [connector delivery](connector-delivery.md#connector-modules). |
| 20 | 2026-11-13 | A released connector becomes a module over two releases, and a family of tools has one definition. | Oracle Database and SQL Server are `bridge` connectors: this release still compiles them in and installs their modules ahead for the connections that use them, and the release after drops them from the core, which finds the modules in place. A connection whose module isn't there at that start keeps its tools, as the type's signed row describes them, until the module arrives; nothing runs without the connector. A tool that a module shares with a compiled-in type (`sql_query`) is registered and published as the core defines it when only its wording differs; any other difference keeps the module's types out. See [connector delivery](connector-delivery.md#the-bridge-between-two-releases). |
| 21 | 2026-11-13 | A person may install a connector module from a file; one that GateRook's list doesn't pin is trusted as an unsigned plugin is. | This narrows decision 19: the trust of a built-in connector still comes only from the signed list, which now also recognises its own packages when they arrive as files (an installation without the network). Any other package is the person's own module. It keeps a module's interface and plain names, but every tool starts in Approval, Read only is a confirmation per tool bound to the package, a person approves the call's arguments rather than the module's description, it shares no name with another connector, and the list never updates or restores it. Refusing such files would have left no way to run a connector built from this repository with changes; trusting them as GateRook's own would have let unreviewed code pass for it. See [a module from a file](connector-delivery.md#a-module-from-a-file). |
| 22 | 2026-11-13 | ClickHouse, DuckDB, H2 and Microsoft Access are connector modules, not catalog plugins. | They are GateRook's own connectors, and as plugins each needed a review and an install step before the first connection. As modules they are cards among the built-in types, arrive when one is chosen, and update by themselves; their reads start in Read only and a person approves the connector's own exact action. They exist only as modules, and no build compiles them in (decision 23 says where their code lives). No release ever carried a plugin catalog, so nothing installed is carried over. See [connector delivery](connector-delivery.md). |
| 23 | 2026-11-13 | The modules that are built against the connector API alone live in the modules repository. | ClickHouse, DuckDB, H2 and Microsoft Access use nothing of the application but the connector API, so their source, tests and documents moved to [gaterook/gaterook-plugins](https://github.com/gaterook/gaterook-plugins), the repository their packages are published from. Its build stands on its own: it takes `connector-api`, `plugin-protocol` and `plugin-host` from the local Maven repository and gives the released packages byte for byte. The connector API's artifact now has the API's version, which such a build names. That repository also describes the module architecture for anyone who writes a module, with the smallest one as an example. Apache Cassandra and Neo4j stay here because they are built from the shared connector code of this repository, which is no stable interface; Oracle Database and SQL Server stay because this release still compiles them in. See [connector delivery](connector-delivery.md#connector-modules). |
| 24 | 2026-11-13 | Every build reads GateRook's published list of connector modules, in the background. | Until now only a release read it, so a build from the repository offered none of the modules GateRook publishes and a search for one found nothing. Now a development build reads the list as a release does; only this repository's tests say `gateway.lists=none`, and a release ignores that. The core reads the list two seconds after the start without anyone waiting for it, says `module.list` when it accepts another list, and the open pages read the connector types again. Connectors › Catalog lists GateRook's modules that aren't installed beside the plugin catalog's entries, and its **Add connection** installs one as the wizard does. **Check now** there checks both lists at once, for a person who doesn't want to wait for the next check. The development launcher gives the core the module host of the checkout's build, so a module also runs there. See [connector delivery](connector-delivery.md#the-channel). |
| 25 | 2026-11-13 | Java packages and the Maven groupId are `com.gaterook`, after the product's domain. | This replaces the `ai.msrv.gaterook` of decision 11 for Java and Maven. Every class has a new binary name, so the connector API is 2.0.0: plugins and modules built against 1.x no longer load, and nothing keeps the old names working, because no installation has a plugin or a module yet. Modules and plugins declare `connectorApi` `>=2.0.0 & <3.0.0`; an application with API 1.x keeps choosing the module versions built for it. The published list holds only modules built for 1.x until versions for 2.0.0 are published, so a build of this repository that reads it (decision 24) offers none of them until then. The application identifiers (`ai.msrv.gaterook.desktop`, `ai.msrv.gaterook.unlock`) and the MCP `_meta` keys (`ai.msrv.gaterook/…`) are not packages and keep their names. |

**Naming contract:** native builds produce `gaterook-core`, deep links use `gaterook://`, and bridge bundles use `gaterook-<endpoint>.mcpb`. Maven artifact IDs and plugin resource names remain stable. The documented development launcher uses a repository-local home, independent of either production home; existing installations are not migrated automatically.
