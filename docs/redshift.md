# Control AI access to Amazon Redshift

GateRook's MCP Firewall lets AI apps explore Redshift schemas and run SQL reads in read-only transactions, and holds every change for your review with Redshift's own plan. The [security model](security.md) explains execution controls, explicit Bypass, and the append-only, tamper-evident audit trail.

## Connect a warehouse

The built-in **Amazon Redshift** connector (`redshift`) calls the [Redshift Data API](https://docs.aws.amazon.com/redshift/latest/mgmt/data-api.html) in one region, signed with SigV4. There is no JDBC driver or Redshift SDK in GateRook; calls go only to `redshift-data.<region>.amazonaws.com` (`.amazonaws.com.cn` in China), and the form's suggestions also to Redshift, Redshift Serverless and Secrets Manager in that region. Choose:

- the **warehouse**: a provisioned cluster by its identifier, or a Redshift Serverless workgroup by its name or ARN, and the **database** to connect to;
- how the Data API **signs in** to the database: as the AWS identity itself (database user `IAM:<user>` or `IAMR:<role>`), as a database user with temporary credentials (clusters only), or with the user of a Secrets Manager secret. The Data API gets the password or the temporary credentials itself; GateRook never sees a database password;
- the **AWS credentials**: an access key (stored encrypted in GateRook) or an AWS profile of this computer, optionally with a **role to assume** and its external ID, as for [DynamoDB](dynamodb.md).

With a role, **Session policy** defaults to each call's own permissions, which AWS enforces whatever the role itself may do: the Data API actions of the call on this cluster or workgroup only, describing, fetching, cancelling and listing only the statements this role session ran (`redshift-data:statement-owner-iam-userid`), and the one way of signing in: `redshift:GetClusterCredentials` for this database user and database, `redshift:GetClusterCredentialsWithIAM` for this database, `redshift-serverless:GetCredentials` for this workgroup, or `secretsmanager:GetSecretValue` on this secret. A workgroup entered by name is scoped to every workgroup of the region; enter its ARN to name it. Reads get `BatchExecuteStatement` and the metadata calls, an approved change only `ExecuteStatement`. IAM can't tell a read from a write in SQL: the session policy keeps a call to its warehouse, database and sign-in, and the database user's grants decide what SQL may do. On prod the session policy can't be turned off.

**Test connection** reports the identity AWS sees (`sts:GetCallerIdentity`), lists the database's schemas and runs a read in a READ ONLY transaction, which names the database user. It warns when that user is a superuser, when calls run without a role, and when the AWS profile runs a command to get its credentials. The periodic health check calls `ListStatements`, which runs nothing on the warehouse, so it never wakes a Serverless workgroup or a paused cluster.

While you fill in the form, GateRook suggests the profiles of `~/.aws/config` and fills in the profile's region. Once it can sign in, with the same credentials as Test connection and a session policy that adds only listings, it lists the region's provisioned clusters (`redshift:DescribeClusters`) and Serverless workgroups (`redshift-serverless:ListWorkgroups`, `ListNamespaces`), even before you enter one, and for a secret sign-in the secrets' names and ARNs (`secretsmanager:ListSecrets`, which returns no values). Databases come from the Data API's `ListDatabases` on an available cluster, signed in as the form says, and from a Serverless workgroup's namespace: a suggestion never wakes a workgroup or resumes a paused cluster. **Database** starts as `dev`, the database Redshift creates by default.

## Bound reads and review exact changes

| Tool | What it does | Default mode |
| --- | --- | --- |
| `redshift_list_schemas` | Schemas of the connection's database | Read only |
| `redshift_list_tables` | Tables, views and their kinds in one schema | Read only |
| `redshift_describe_table` | Columns with their types, nullability and defaults | Read only |
| `redshift_query` | One `SELECT`, `WITH`, `SHOW` or `EXPLAIN`, with `:name` parameters | Read only |
| `redshift_execute` | One change: DML, DDL, `TRUNCATE`, `VACUUM`, `ANALYZE`, `REFRESH MATERIALIZED VIEW` | Approval |

A read runs as one `BatchExecuteStatement` in `AUTO_COMMIT` mode: `SET statement_timeout` to the policy's statement timeout, `BEGIN READ ONLY`, the statement, `ROLLBACK`. In its default `TRANSACTION` mode the Data API would wrap the batch in a transaction of its own and commit it at the end, and a `BEGIN READ ONLY` inside it wouldn't hold; in `AUTO_COMMIT` it wraps nothing, so the statement runs in the READ ONLY transaction, which Redshift enforces, and the rollback ends it. GateRook uses a result only when Redshift reports that `BEGIN READ ONLY` finished, and reports a write Redshift refused in it as denied. A query still running at the call's deadline is cancelled.

Pass values as `:name` parameters. The Data API passes each as text that Redshift casts; it can pass neither `NULL` nor an empty value, so write those in the SQL. Answers keep Redshift's types: a whole number is a JSON number only where JavaScript keeps it exact, `numeric` stays text, `timestamp` is ISO 8601 and `timestamptz` ISO 8601 in UTC, `SUPER` is JSON when it fits a cell, binary values show their first 256 bytes in hex, and long strings are cut to the endpoint's cell size. Each answer reports the statement, its rows and bytes. A large result returns `nextCursor`, which reads on from the same row of the same statement's result without running the query again; Redshift keeps a result for 24 hours, and so long a cursor lives. Cursors are sealed by GateRook and belong to one connection and one request.

GateRook first reads each statement by the tokens of Redshift's SQL: `'…'` strings and `"…"` names with doubled quotes, `--` and block comments. It refuses what it can't read with certainty: an open quote or comment, a comment inside a comment (readers disagree on nesting), a backslash in a string (Redshift may read it as an escape, which would move where the string ends), a dollar-quoted body and a control character. It also refuses more than one statement; `GRANT` and `REVOKE`; users, roles, groups, databases, default privileges, row-level security and masking policies, ownership (`OWNER TO`, `AUTHORIZATION`); `COPY` and `UNLOAD`, which move data to and from S3, and external schemas, tables and functions, storage locations, datashares, models and libraries, which reach S3, Lambda, other databases, SageMaker or other accounts; `CALL`, functions and procedures; transaction and session control (`BEGIN`, `COMMIT`, `SET`, `SET SESSION AUTHORIZATION`, `RESET`, `LOCK`, cursors, prepared statements, `CANCEL`); `SELECT … INTO`, `EXPLAIN ANALYZE`; and functions that stop other sessions, change their priority or change settings (`pg_terminate_backend`, `pg_cancel_backend`, `change_*_priority`, `set_config`).

What holds a read is, in order: GateRook sends `redshift_query` only what it reads as one of the four reads; Redshift runs it in a READ ONLY transaction and stops it at the statement timeout; the database user's grants decide what it may read. GateRook doesn't follow views or functions: a read of a view reads its base tables, and a Lambda UDF a read calls runs outside Redshift, where the READ ONLY transaction doesn't reach. Give the reading database user `USAGE` and `SELECT` on the schemas agents read, and no `EXECUTE` on external functions.

`redshift_execute` runs one change. Before a person is asked, GateRook runs `EXPLAIN` of an `INSERT`, `UPDATE`, `DELETE` or `CREATE TABLE … AS` in a transaction that is rolled back; Redshift plans only those, and other statements are shown as written. A statement whose plan Redshift refuses is never put to a person. The approval shows the exact statement, its parameters, its target, Redshift's row estimate and plan. What runs is the approved statement, once, as `ExecuteStatement` with a client token derived from the approval, which the Data API keeps for 8 hours. A change is never retried: an answer lost after the request was sent reports the outcome as unknown, and a change still running at the call's deadline is left running and reported as unknown with its statement id. A statement Redshift stops changes nothing; `TRUNCATE` commits at once and can't be rolled back.

## Verify

The connector's tests run against a fake of the Data API, STS and the listings of the form's suggestions in every build; there is no Redshift emulator. They check the requests, their signatures and session policies, not Redshift's behaviour: that a READ ONLY transaction refuses a write, the text of a plan and the statement states come from AWS's documentation. JVM checks do not establish native-image or installer compatibility, nor behaviour against Redshift itself.

AWS documents the [Data API](https://docs.aws.amazon.com/redshift-data/latest/APIReference/Welcome.html), [BatchExecuteStatement and its execution modes](https://docs.aws.amazon.com/redshift-data/latest/APIReference/API_BatchExecuteStatement.html), [`BEGIN … READ ONLY`](https://docs.aws.amazon.com/redshift/latest/dg/r_BEGIN.html), [`EXPLAIN`](https://docs.aws.amazon.com/redshift/latest/dg/r_EXPLAIN.html), [IAM for the Data API](https://docs.aws.amazon.com/redshift/latest/mgmt/data-api-iam.html) and [session policies](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html#policies_session).
