# Будущий перенос приложения и дизайн-кита

**Статус: перенос не начат.** Этот документ фиксирует наблюдаемый контекст и необходимые проверки. Он не подтверждает наличие исходников, успешные сборки или готовность релиза в данном репозитории.

## Контекст существующей реализации

Переносимое приложение использует Electron, Angular и Java/Spring Boot; ядро упаковывается как GraalVM native image. npm объединяет `ui`, `desktop` и `bridge`, а дизайн-кит является отдельным пакетом. UI ссылается на него через `file:../design` внутри того же репозитория.

Java-часть собирается Maven reactor и включает ядро, коннекторы, API, плагины, plugin host и CLI-мост. В наблюдаемой конфигурации используются Java 25 и Node 24. Точные версии следует перенести из реальных манифестов и файлов фиксации версий, а не из этого описания.

Существующий staging включает UI, native-ядро и SQLite-библиотеку, jlink JRE, plugin-host JAR, мосты и закреплённую версию cloudflared. Конфигурация Electron Builder содержит DMG/ZIP для macOS, NSIS EXE для Windows, AppImage/DEB для Linux.

Существующий release workflow описывает пять целей: Linux x64/arm64, macOS x64/arm64, Windows x64. Он запускается по тегу или вручную, сохраняет установщики, blockmap и манифесты обновления, объединяет macOS-манифесты и создаёт draft GitHub Release. Подпись и нотариализация зависят от секретов CI; без них предусмотрены неподписанные либо ad-hoc сборки. Наличие этих настроек не доказывает успешную проверку всех платформ.

## Что сохранить при переносе

- Исходники, Maven-модули, npm-пакеты, lock-файлы и точные версии инструментов.
- Тесты, фикстуры, метаданные native image, локальные тестовые сервисы и связанные проверки.
- Сборку, staging, упаковку, конфигурацию подписи и зависимости, необходимые установщику.
- Дизайн-токены, SCSS, компоненты, шрифты, иконки, брендовые ресурсы, генераторы, инвентарь и локальные инструкции.
- Актуальные архитектурные решения и документацию разработки, предварительно проверив пригодность материалов для публичного репозитория.
- Лицензии и уведомления сторонних компонентов. Лицензию самого продукта не выбирать автоматически.

Не переносить рабочие данные пользователей, секреты, локальные настройки IDE, кэши, установленные зависимости и результаты сборок как исходный код. Отдельно определить, какие генерируемые ресурсы уже являются версионируемыми частями кита; не исключать их общим правилом для всех каталогов `dist`.

## Разделение сайта и кита

В существующем ките находятся и общие UI-ресурсы, и публичный сайт: промостраница, контент документации, скрипты генерации страниц и статического экспорта, поведение кнопок скачивания. Текущий экспорт сайта формирует `site-dist/`; это результат сборки, а не канонический источник.

При переносе:

1. Сохранить канонические токены, общие компоненты, ресурсы и проверки кита в `gaterook`.
2. Передать публичные страницы, контент и сборку сайта в `gaterook-platform`, сохранив происхождение и необходимые лицензии.
3. Определить воспроизводимую поставку конкретной версии кита платформе. Не создавать второй редактируемый комплект одинаковых компонентов.
4. Проверить зависимости генераторов, SCSS, ассетов, инвентаря и ссылок после разделения. Не предполагать, что сайт можно отделить простым копированием одной HTML-страницы.
5. Проверить, что публичный экспорт не включает приватные материалы и эталонные экраны приложения по ошибке.

## Аудит имён, идентификаторов и URL

В переносимой реализации остаются старые технические имена и продуктовые надписи. Для каждого изменения отдельно оценить совместимость:

- Отображаемое имя, package metadata, иконки, copyright и название установщика.
- `appId`, Windows AUMID, схема deep link, Java-пакеты и идентификаторы приложения.
- Путь пользовательских данных, настройки клиентов, автозапуск и механизм обновления существующих установок.
- GitHub owner/repository, адрес update provider, ссылки документации, сайта и скачивания.
- Теги, номера версий, имена артефактов и метаданные обновлений.

Использовать **GateRook** как имя продукта и `gaterook` как технический слаг. Не выполнять глобальную замену строк без проверки ссылок и поведения. Пока настоящие установщики не опубликованы, сайт не должен выдавать отсутствующие загрузки за доступные.

## Порядок будущей работы

1. Зафиксировать выбранную исходную ревизию в рабочем плане миграции и проверить состав файлов; не раскрывать закрытые сведения в публичных документах.
2. Перенести приложение, кит и необходимые зависимости сборки с сохранением структуры и лицензий.
3. Разделить ответственность сайта и общих ресурсов, описать контракт с платформой.
4. Перенастроить имена, URL и CI на новый репозиторий; проверить совместимость пользовательских данных и обновлений.
5. Добавить реальные команды разработки и проверки в `README.md` и `AGENTS.md` на основе перенесённых манифестов.
6. Проверить самостоятельный клон приложения, затем связанный процесс получения артефактов платформой.

## Критерии завершения переноса

- Сборка не читает файлы соседнего репозитория или старой рабочей папки.
- Проверки Java, UI, Electron и дизайн-кита выполнены в объёме перенесённого изменения; ограничения по платформам перечислены явно.
- Не потеряны runtime-ресурсы установщика, лицензионные файлы и метаданные native image.
- Для заявленных платформ проверены артефакты и установка; статус подписи/нотариализации указан точно.
- Описано, как платформа выбирает ревизию, запускает сборку и получает согласованный набор артефактов.
- Публичные документы отражают реальное состояние; подготовительный статус снят только после выполнения переноса.

До переноса исходников сборка и эти проверки недоступны. Текущую подготовку можно проверить по ссылкам документации, составу файлов и `git diff --check`.
