# Control AI access to an H2 database

GateRook's MCP Firewall lets AI apps read an H2 database on an H2 server through checked queries that are always rolled back, and holds every change for your review. The [security model](security.md) explains execution controls, explicit Bypass, and the append-only, tamper-evident audit trail.

## Install the H2 plugin

H2 is a plugin, not a built-in connector: its code runs in a plugin host, a separate Java process with its own data folder, started by GateRook ([architecture](ARCHITECTURE.md#75-plugins-catalog-and-external-mcp-servers)). The plugin is one JAR, `gw-h2-1.0.0.jar`, with the H2 client 2.5.252 unmodified inside it. H2 is under the Mozilla Public License 2.0 (or the Eclipse Public License 1.0); the JAR carries the license and says where H2's source is (`META-INF/LICENSE-H2.txt`).

- **From the catalog.** Once the signed catalog lists H2, open **Connectors → Catalog** and install it. The review shows its tools and that it opens TCP connections to the host and port of each connection.
- **From a local build.** `mvn -B -ntp -pl plugins/h2 -am package -DskipTests` writes `plugins/h2/target/gw-h2-1.0.0.jar`; the build is reproducible. Open **Connectors → Catalog → Install from file or URL** and choose it. A JAR that no catalog you trust lists is reviewed as an **unsigned plugin**.

The plugin needs connector API 1.1, the first with TCP destinations: an older GateRook refuses to install it, since its plugin host wouldn't check the plugin's connections. Every tool of a plugin starts in **Approval** on every endpoint; you can set the three reads to **Read only**.

## Connect to an H2 server

A connection is one database of an H2 server started with `-tcp` (H2's TCP server, port 9092 by default):

- the **host** and **port** of the server;
- the **database** as the server names it: `~/orders`, `./data/orders`, `/srv/h2/orders` or `mem:orders` for an in-memory database another connection keeps open;
- the **user** and its **password**, which GateRook stores encrypted and hands the plugin for one call at a time; leave the password empty for a user without one, as H2's `sa` often is.

GateRook builds the URL from these fields only (`jdbc:h2:tcp://host:port/database;IFEXISTS=TRUE`): a database name with `;` is refused, so no H2 setting (`INIT=`, a mode, a trace file) comes from anywhere else, and the plugin never creates a database. That matters because a server started with `-ifNotExists` would create a missing one and make the connecting user its administrator.

H2's TCP protocol isn't encrypted, so the plugin connects only to a server on this computer or a private network; reach a remote one through an SSH tunnel or a VPN. The H2 client opens its own sockets, and the plugin host's [TCP gate](ARCHITECTURE.md#75-plugins-catalog-and-external-mcp-servers) lets them reach the connection's host and port only. A private address, `127.0.0.1` included, must also be allowed for the connection in its environment's policy (`http.allowedPrivateRanges`), as for a plugin's HTTP requests: **Test connection** then names the range to allow, such as `Allow 10.30.4.12/32 for warehouse on dev`. Cloud metadata, link-local addresses and GateRook's own ports are never reachable. Each call opens its own connection and closes it.

**Test connection** connects, reports the H2 version and the user, and reads what the user may do. An administrator gets a warning (outside dev a danger): H2 has no read-only transactions, so an administrator's reads are only as safe as GateRook's checks, and the database's own views and functions run with its rights. Give agents a user with SELECT rights only:

```sql
CREATE USER AGENT PASSWORD 'choose-a-password';
GRANT SELECT ON SCHEMA PUBLIC TO AGENT;
```

Rights a user holds through a role other than `PUBLIC` aren't shown: H2 shows only an administrator who has which role.

## Bound reads and review exact SQL

| Tool | What it does |
| --- | --- |
| `h2_list_tables` | The tables and views by schema, with estimated rows and comments |
| `h2_describe_table` | One table's or view's columns, primary key, foreign keys and indexes, and a view's query |
| `h2_query` | One query: SELECT, WITH … SELECT, VALUES, TABLE, EXPLAIN or SHOW |
| `h2_execute` | One INSERT, UPDATE, DELETE, MERGE, TRUNCATE, COMMENT ON or DDL statement, after approval |

`h2_query` runs one query as the connection's user in a transaction GateRook always rolls back, with the row limit of the call, the connection and the environment, and the statement timeout of the environment or the connection, whichever is stricter. Before anything reaches the server, GateRook reads the statement by H2's tokens (strings, quoted names, `$$` strings, `--`, `//` and block comments) and refuses what it can't read with certainty: a nested comment, an unclosed string, more than one statement, a brace (JDBC escapes such as `{call …}`, which H2 would turn into `CALL`), `@`, `#` or a backtick. A query may call only H2's built-in functions, without those that reach outside the database: `FILE_READ`, `FILE_WRITE`, `CSVREAD`, `CSVWRITE`, `LINK_SCHEMA`, `CANCEL_SESSION` and `ABORT_SESSION`. A function the database defines (an alias with Java code), a function named with its schema or in quotes, a function only a compatibility mode adds, data change tables (`FINAL TABLE (INSERT …)`), `NEXT VALUE FOR` and `NEXTVAL` (a rollback doesn't undo a sequence), `FOR UPDATE`, `EXPLAIN ANALYZE`, `CALL`, `SET`, scripts, backups, transactions and `EXECUTE IMMEDIATE` are refused. Views and functions keep the behaviour the server gives them: the rollback undoes a write they make in the transaction, the user's rights bound the rest.

Answers keep H2's types: integers are JSON numbers where JavaScript keeps them exact, decimals are text, dates and times are ISO-8601 (with the offset where the type has one), binary values show their first 256 bytes in hex, arrays are arrays and `JSON` values are JSON. A `JAVA_OBJECT` value is never deserialized: it shows as its bytes.

`h2_execute` runs one statement on tables, views, indexes, sequences, schemas, domains, constants or synonyms, exactly as approved, and commits it once. H2 commits DDL as it runs it, so a DDL statement can't be rolled back. The approval shows the statement and the table it names. Java code (`CREATE ALIAS`, `CREATE TRIGGER`, `CREATE AGGREGATE`, a table `ENGINE`), linked tables, users, roles, rights, settings, scripts, backups, `SHUTDOWN`, and the functions that reach outside the database are refused even with approval. A change is never retried: an answer lost after the statement ran reports the outcome as unknown.

## Verify

The plugin's tests run against an H2 server in the test JVM: the tools, H2's types, limits and timeouts, refusals, an approved change and what a test says about an administrator, a reader and a writer. `H2PluginHostIT` loads the release JAR in a real plugin host (on macOS under the core's `sandbox-exec` rules) and checks that the H2 client reaches the server through the TCP gate under a grant that allows this computer, that the same connection is refused without the policy's private range with the range to allow, and that a grant for another port lets nothing through. These tests don't establish behaviour against other H2 versions, on Linux or Windows hosts, or in a native image.
